# 4편 지시문 — 시스템 관리자와 문서 열람 권한을 나누기

아래를 AI 코딩 도구에 그대로 준다.

---

부서 이동과 퇴사 처리를 화면에서 할 수 있게 **관리 화면**을 만든다.
그 화면을 쓰는 **시스템 관리자**는 계정과 조직을 고칠 수 있지만, 그것만으로 다른 부서의 글을 읽을 수는 없다.

## 먼저 정한 것 (이 예제의 규칙)

- 권한은 "무엇을 할 수 있나"로 나눈다. 시스템 관리자 역할이 주는 것은 **계정·조직 관리** 하나뿐이다.
- 게시판을 볼 수 있는지는 계속 `canReadBoard` 가 정한다. 이 함수는 역할을 보지 않는다. 시스템 관리자도 자기 부서 게시판과 전사 게시판만 본다.
- 역할은 요청마다 DB 에서 다시 읽는다. 역할을 빼면 다음 요청부터 바로 막힌다.

## 표 (새 migration `migrations/005_roles.sql`)

- `user_roles(user_id → users.id, role text CHECK (role IN ('system_admin')), PRIMARY KEY (user_id, role))`
- 가상 데이터: `choi`(경영지원팀)에게 `system_admin` 을 준다.

## 코드

- `src/auth.js` 의 `loadUser` 가 `req.user.roles`(문자열 배열)를 채운다.
- `src/policy.js` 에 `canManageUsers(user)` 를 더한다. `roles` 에 `system_admin` 이 있을 때만 true.
- 관리 화면 (`src/routes/admin.js`). 모든 경로가 서버에서 `canManageUsers` 를 거치고, 아니면 `notFound` (404).
  - `GET /admin/users` 직원 목록: 이름, 아이디, 부서, 직급, 상태(재직/퇴사), 역할
  - `GET /admin/users/:id` 한 사람: 소속 이력 표, 부서 이동 폼(부서 선택, 직급), 퇴사 처리 버튼
  - `POST /admin/users/:id/transfer` (필드 `department_id`, `title`) → `transferUser` 를 부르고 `/admin/users/:id` 로 302. 실패하면 400 과 오류 문구
  - `POST /admin/users/:id/offboard` → `offboardUser` 를 부르고 `/admin/users/:id` 로 302. 실패하면 400
  - 자기 자신은 퇴사 처리할 수 없다(400). 관리자가 한 명도 없게 되는 것을 막는다.
- 왼쪽 메뉴에 `관리` 를 더하되 `canManageUsers` 인 사람에게만 보인다. (메뉴를 숨기는 것은 편의이고, 막는 것은 위의 서버 검사다)

기존 확인도 계속 통과해야 한다. 끝나면 `npm run check` 로 확인해 줘.
