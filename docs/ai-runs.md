# AI 에게 지시문을 주고 만든 기록

각 편의 `done` 코드는 Claude Code 에게 그 편의 `prompts/epNN.md` 만 주고 만들게 한 결과다. 사람은 결과를 검토하고, 지시문이 모자랐던 곳을 고쳤다.
AI 는 저장소 안의 기존 코드와 확인 스크립트(`checks/`)를 읽을 수 있었다. 여러분이 따라 할 때와 같은 조건이다.

여기에는 편마다 **지시문에 없어서 AI 가 스스로 정한 것**과 **AI 가 스스로 밝힌 남은 약점**을 적었다.
여러분의 AI 가 다르게 정했다면, 어느 쪽이 내 시스템에 맞는지 정하는 것이 사람의 몫이다.

| 편 | 확인 | 확인을 돌린 횟수 |
|---|---|---|
| 1 부서 게시판 | 13 / 13 | 1번에 통과 |
| 2 부서 이동 | 21 / 21 | 1번에 통과 → 지시문을 고친 뒤 다시 통과 |
| 3 퇴사 처리 | 29 / 29 | 1번에 통과 |
| 4 관리 화면 | 38 / 38 | 1번에 통과 |
| 5 첨부·내보내기 | 48 / 48 | 1번에 통과 |
| 6 열람 기록 | 59 / 59 | 2번, 둘 다 통과 (사이에 README 만 바뀜) |
| 7 백업·복원 | 65 / 65 | 2번, 둘 다 통과 (사이에 README 만 바뀜) |
| 8 승인 요청 | 75 / 75 | 2번, 둘 다 통과 + 동시 처리 확인만 5번 더 → 모두 통과 |

## 1편 부서 게시판

- 스스로 정한 것: 권한을 입력 검사보다 먼저 본다(볼 수 없는 게시판이면 제목이 비어도 404). 주소의 번호는 15자리까지만 받는다. 제목·본문 길이를 DB 제약으로도 건다.
  게시판 목록은 전체를 읽은 뒤 `canReadBoard` 로 거른다(판단을 한 곳에 두려고).

## 2편 부서 이동

- **사람이 고친 지시문.** 처음 지시문은 "옮기는 날 전날로 닫는다"와 "종료일은 시작일보다 앞설 수 없다"를 함께 요구했다.
  시작한 날 바로 옮기면 둘을 함께 지킬 수 없다. AI 가 이를 짚었고, 사람이 "기간은 시작일부터 종료일 **전날**까지, 옮기는 날이 곧 종료일"로 정했다.
- 스스로 정한 것: 직급만 바뀌는 이동을 받는다. 옮기는 날이 지금 소속의 시작일보다 앞서면 거부한다(뒤에 지시문에 넣음). 새 글의 소속은 세션이 아니라 저장하는 순간 DB 에서 읽는다.

## 3편 퇴사 처리

- 스스로 정한 것: 퇴사자도 비밀번호 검증을 거친 뒤 상태를 본다(응답 시간 차이를 줄이려고). 미래 날짜 퇴사도 즉시 끊는다(예약 퇴사 없음). 복직 경로는 없다.
- 남은 약점: 없는 아이디와 퇴사자의 응답 시간 차이는 그대로다.

## 4편 관리 화면

- 스스로 정한 것: 역할 부여는 migration 이 아니라 가상 데이터(seed)에서 한다. 로그인하지 않은 `/admin` 요청은 로그인 화면으로 보낸다. 업무 오류는 400, DB 오류는 500.
- 남은 약점: "관리자가 한 명도 없게 되는 것"은 자기 퇴사 금지로만 막는다. 관리자 둘이 동시에 서로를 퇴사 처리하면 0명이 될 수 있다. DB 에서 역할 행을 직접 지우는 것은 막지 않는다.

## 5편 첨부·내보내기

- **AI 가 지시문이 만들 구멍을 막았다.** 지시문은 "CSRF 검사는 multipart 요청을 건너뛰고, 올리기 경로에서 본문을 읽은 뒤 검사한다"였다.
  그대로 하면 본문이 필요 없는 다른 POST(로그아웃, 퇴사 처리)를 multipart 로 보내 토큰 검사를 피할 수 있다. AI 는 올리기 주소가 아닌 multipart POST 를 403 으로 막았다.
  이 동작은 확인 스크립트가 없고, AI 가 손으로 한 번 확인했다.
- 스스로 정한 것: 검사 순서(로그인 → 글 열람 404 → 글쓴이 403 → 본문 읽기 → CSRF → 파일 유무). 권한을 본문 읽기 전에 봐서 거부된 요청의 파일은 디스크에 닿지 않는다.
  파일 폴더가 `public/` 안이면 시작할 때 오류. 내려받기에 `Cache-Control: private, no-store`.
- 남은 약점: 올리는 도중 부서 이동·퇴사가 일어나면 그 한 건은 저장된다. 첨부 삭제·개수 제한이 없다. 서버가 올리는 중 죽으면 주인 없는 파일이 남을 수 있다.
  파일 종류 검증과 내용 검사가 없다. CSV 수식 방지는 `=` `+` `-` `@` 네 가지만 처리한다.

## 6편 열람 기록

- **가장 중요한 한계.** 이 예제에서는 앱이 쓰는 DB 계정이 곧 기록 표의 주인이다. 트리거가 `UPDATE`·`DELETE`·`TRUNCATE` 를 막지만, 표의 주인은 트리거를 끄거나 지울 수 있다.
  앱 계정으로 고칠 수 없게 하려면 `INSERT`·`SELECT` 만 가진 계정을 따로 둬야 한다. DB 관리자의 변경까지 막으려면 기록을 다른 곳에 따로 보관해야 한다.
- 스스로 정한 것: 로그인 실패는 `denied`, 없는 대상은 어느 종류든 거부로 기록하지 않는다. 기록을 넣지 못하면 요청 자체를 실패시킨다.
- 남은 약점: 로그아웃, 관리 화면 열람 시도, 글쓰기 화면 열람 시도, CSRF 실패, 400 업무 오류는 기록되지 않는다. 읽기 기록은 응답을 보내기 전에 넣는다.

## 7편 백업·복원

- 스스로 정한 것: "같은 시점"을 DB 스냅샷 하나로 보장한다(`pg_export_snapshot` → `pg_dump --snapshot`, 목록표 숫자도 같은 스냅샷에서).
  파일 묶음에는 행이 가리키는 파일만 넣는다. 원본에서 행의 파일이 없거나 크기가 다르면 백업을 거부한다.
  표마다 행 수뿐 아니라 내용 지문도 저장한다(행 수만으로는 바뀐 행을 못 잡는다).
- 실제로 일어난 일: AI 가 손으로 해 본 첫 백업이 거부됐다. 앞선 확인이 남긴 첨부 행의 파일이 이미 지워져 있었다. 의도한 동작이다.
- 남은 약점: 파일 풀기가 DB 복원 뒤에 실패하면 대상 DB 는 채워진 채 남는다. 내용 지문은 양쪽 PostgreSQL 판이 같다고 가정한다.
  백업은 암호화되지 않았고 비밀번호 해시를 담고 있으며 같은 기계에 있다.

## 8편 승인 요청

- 스스로 정한 것: 응답 순서 404 → 403 → 409 → 400. 지시문에 없던 DB 규칙(끝난 요청과 제목·본문·당사자를 바꾸는 `UPDATE` 를 막는 트리거 등).
  승인자 행을 `FOR SHARE` 로 잠가, 확인한 뒤 저장하기 전에 승인자가 퇴사 처리되는 경우를 막는다.
- 남은 약점: 승인자를 넘기는 기능이 없다. 올린 사람이 퇴사하면 대기 요청이 남는다. `DELETE` 는 막지 않는다.
